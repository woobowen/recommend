# GitHub 上传与实验交付说明（学弟适用）

适用于 `woobowen/recommend` 中由你负责的研究分支。依据 2026-11-21 确认的 v1.5 `PROJECT_RULES.md` 第 3、4、8、9 节和 `REMOTE_EXECUTION.md` 第 3–9 节整理。方案、训练与资源使用仍按每次任务约定。目录与文件名可沿用现有工程。 [项目规范](../../../PROJECT_RULES.md) · [远端执行规范](../../../REMOTE_EXECUTION.md)

## 1. 确认工作分支与版本

先根据实际分工、历史发布和项目材料确认本次工作属于哪个分支。使用该分支已有的代码与目录结构。共同维护、代上传或归属不明时，在分支说明中记清负责人、谁上传了什么、各自能改的范围；归属未清的内容先保留并继续核查。公共分支的修改依照明确分工和授权。发布前用 `git status --short --branch`、`git diff`、`git diff --cached` 和上游差异核对现有未提交、暂存及未推送成果，逐路径纳入本次内容。需要隔离时从现有目标分支的固定提交准备工作副本；保护活跃作业依赖的快照。

研究文档同时记下实际运行源码版本、结果发布版本和后续补件版本。服务器源码无 `.git` 时，记下导出的固定 commit、路径以及有差异的文件及其内容身份。涉及仓库外模块、本地补丁或启动器，把真正参与执行的文件和来源一并保留。

## 2. 建立分支 README 和代码导航

README 应让读者找到研究问题、主要实验与当前状态、负责人、版本关系和材料入口。已有基线或上游材料在合适的地方引用固定路径。说明原件、运行所需工程适配与研究变更的位置及用途。给核心模块标出真实路径、相关类或函数、调用方和后继处理、输入输出、格式或关键轴、影响行为的配置、关联实验。工具与测试可按用途分组，上游与自动生成内容说明来源和版本。

README 可按以下段落填写，尖括号内容用本分支真实材料替换。

```text
用途与维护范围    <研究问题、基线关系、维护人、已有分工>
实验入口          <实验名、实验说明相对路径、计划与实际状态>
代码入口          <真实入口→核心类／函数→产物路径，标注配置>
资产入口          <数据、映射、SID、模型等身份和取得说明>
结果与复现        <原始结果、汇总脚本、边界和四种复现起点>
```

沿实际调用说明数据处理、文本编码与 embedding、SID 量化与映射、模型与训练、生成、评价、统计／绘图。若某环节采用固定外部原件，定位上游原件及工作起点。新变体的说明应覆盖路由实际走到的构造、训练或推理路径，并给出相应生效证据。

## 3. 每个实验建立一个主说明

一个主说明可引用同一实验多个数据域、条件、种子和尝试；让配置与机器记录承担详细事实，正文解释研究逻辑。记录研究目标、方案确认出处、基线与对照、改变与固定的条件，以及计划与实际组合、复用对照依据与排除项。对适用实验写清输入和标签、历史边界、位置和 mask、共享或迁移参数、初始化、训练与冻结部分、目标函数、验证选模、生成候选及约束、无效候选与去重。随机化写清操作对象、作用阶段、范围、粒度、种子生命周期以及与对照共用的部分。

执行记录给出固定源码、保存脚本、真实 `argv`、解释器、cwd、模板、命令覆盖和最终配置；记录行为相关依赖、硬件与设备映射、精度、进程、输出和日志。原路径可作为历史证据另存。提供在你的真实环境中可调整的运行说明，明确哪些路径需要填写、读取哪些输入、按什么顺序运行、写入哪里的独立输出。将成功、失败、超时和恢复标为不同尝试；恢复记录给出父尝试、恢复点及实际加载的优化器、随机状态等。发现历史有效配置缺失时，标出已证实的字段和缺件，事后整理文件记录形成时间与依据。

```text
实验 <名称>    <方案出处、基线、固定条件、变动、预期对照>
源码           <运行 commit 或 export 身份、入口和必要差异>
有效配置       <保存的最终配置、argv、环境、输入与输出位置>
运行           <run/job/attempt、计划和实做、状态、时间／时区>
结果           <逐次原始输出→汇总和绘图命令→本次报告>
验收与限制     <核了什么、覆盖多少、有哪些未知／失败>
```

## 4. 输入资产与大文件

为各实验记录实际采用的数据版本、过滤和切分、样本范围、物品编号及其映射。沿原始 item ID → 内部编号 → embedding 行 → SID 列／行 → 模型 token 或 vocabulary 的实际路径核对；注明序列轴、码位、保留特殊 token、码本范围、去重位和无效码规则。保留文本字段、编码器及其权重版本、pooling、归一化、量化方法和真正用于生成的配置。checkpoint、tokenizer、训练配置和输入 SID 分别记录各自身份及配对依据。汇报内容 hash 核对与语义／轴对应核对的覆盖范围。

```text
资产           <用途、实验、来源、固定版本或上游标识>
对象范围       <文件／分片、尺寸、必要 hash、格式与轴含义>
配对与验证     <与输入／权重关系、核对键、覆盖范围和结论>
取得与恢复     <来源入口、访问条件、装配／解压步骤、空间>
```

适合阅读的代码、配置、说明与结果直接提交。大资产使用获准且读者能取得的持久位置，按现有条件选择 LFS 或其他交付渠道。对每个必需对象验证能获取实际 bytes，并与清单对照。分片写明顺序、分片及合并后身份、解包所需空间。外部依赖注明权限和适用许可证。受限时写明谁能取得、依赖哪个权限、哪一步验证受影响。保留已验证且未变化的资产证据，变更时查受影响部分。

## 5. 结果与复现

保存原始或足以复算的单次输出，记录测试集、评价单位与分母、排序/候选口径、合并方式、缺件、去重和重复运行采用规则。按 `(dataset, condition, seed, attempt)` 或实际主键关联结果表。说明绝对变化、相对变化与统计不确定性，明确失败和不利结果。图表导航提供脚本和实际输入，不同切分、前缀或条件的指标避免混合解释。

```text
发布表 <表／图与一行主键>
  ← <统计脚本、配置、汇总命令与分母>
  ← <每个被纳入的原始记录与实际输出>
  ← <job/attempt、选模依据、checkpoint、数据/SID、运行源码和有效配置>
```

| 起点 | 交付和验证 |
| --- | --- |
| 已保存输出复算 | 给原始输出、统计及绘图脚本、实际输入和命令。标出本次核过的格子、图和覆盖范围。 |
| 固定 checkpoint 重新评价 | 给固定权重、配套 tokenizer／映射、数据、生成器与评价入口。记录评价条件、输出和是否实际重评。 |
| 重跑实验 | 给输入、固定源码、兼容环境、有效配置和各阶段入口、顺序、预算与验收。标明哪些阶段实际跑过。 |
| 重建上游资产 | 给原始数据／模型、转换、编码、量化与装配依赖。采用外部原件时标明复现起点和仍需取得的依据。 |

每种起点分别填材料是否具备、实际验证范围与结果、缺件及影响。历史实验补入能取得的原件，或补真实关联。只能事后恢复的配置、映射和脚本注明日期、原始依据以及仍不可恢复的环节。

## 6. 三阶段审核

| 阶段 | 保留什么 | 用什么验收 |
| --- | --- | --- |
| 实验前 | 范围、关键选择的依据、固定源码和实际差异、配置与 argv、输入配对、环境和资源、验证与启动材料 | 静态检查、对照与干预生效证据、在授权范围完成的必要预跑。注明范围、待决项、内部及需要的非作者检查。 |
| 实验中 | 同一 job/attempt、带时区时间、实际进程、step 或进度分子与分母、日志截取范围、异常、占用、输出空间和部分产物 | 查原 job 的真实进展；按项目要求轻量观测。断线记录最后已知状态，用原 job 查接收和进程后决定动作。修正和接续保留旧记录。 |
| 实验后 | 计划与实际完成组合、终态、选模及输入版本、单次原始结果、可复算汇总、发布和检查回执 | 复算必要结果，核对源到表图和材料取得；分别表达实际完成、复算、重评和研究结论。 |

长任务用已有可用服务器 runner，将脚本、输入、日志和状态保存在服务器并独立于 SSH 会话；每条真实记录围绕同一实验身份。记录GPU映射与空闲状况，使用固定快照和独立输出。对历史材料只回溯当前能确认的事实。直接引用未变化的固定版本和先前验证，新增或变更时点明复核范围。重要任务按项目规范由非作者直接读取原件、差异和验证输出，记录实际所读和发现的问题。

## 7. 发布、回读和交付

发布前做到以下检查。

- 用真实目标分支、固定源码、已审核内容核对 staged diff。分支首页能走到每个实验和相关代码、有效配置、资产入口、运行与结果。保留原件和失败尝试。排查忽略文件、无效链接、Git LFS 指针、凭据和无关本地文件。
- 使用 GitHub 正常推送和合适的获准交付渠道。大文件能取得需要实际验证。保留可读的正文、正式源码和配置入口。
- 从应审问题列出所需原文与单次记录，先整理、合并重复说明和字节相同的副本，再无损压缩。相同内容可存一次，注明各版本、路径及 run／attempt 对应。保留实际关键源码及依赖、差异和有效覆盖、运行原件、结果输入与计算程序、失败或异常和非作者审读。按审核用途提取日志或大型结果时，保留原件，随包记录来源、范围、脚本和核对输出，保全所需数值精度和完整覆盖。
- 把全部必审材料装入一个完整 ZIP。固定链接供交叉核对和溯源，包内应能直接找到真正需要检查的内容。解压后检查导航、实际内容、CRC、成员数量、重复及危险路径和敏感信息。ZIP 的整体 SHA-256 放包外。发布后实际下载校验，交给用户可直接取得的同一个 ZIP；有渠道限制时换能取得完整文件的渠道。

发布后回读实际远端 ref 和关键文件，记录完整 commit、检查时间及实际访问范围。将具备权限的实际载荷与包外校验值比对。后续提交改变受审内容时复查受影响文件。交给用户和网页 GPT 的材料应包含分支和固定版本入口、实际运行源码与服务器对应、各实验终态及复现范围、原始结果到表图、非作者直接检查证据、未决事项、证据包可取得入口、大小及 SHA-256。仍需用户上传必要证据时标明 `GPT_UPLOAD_REQUIRED: YES`，全部已可获取时标明 `NO`。明确要求打包的任务仍交付已校验的实际包。
